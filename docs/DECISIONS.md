# Decisions

Dated decisions with reasons. Newest at the bottom of each day.

## 2026-10-26

- **Python 3.12 venv in `.venv`.** The Mac's default `python3` is 3.14; 3.12 is used for the venv and CI because every dependency we need (numpy, pyserial, PlatformIO) has mature wheels for it. The code still targets Python 3.10+.
- **Pinned dependencies.** `numpy==2.5.4`, `pytest==9.1.1` (the versions that installed and passed the 17 tests on this Mac). Pinned so a later reinstall reproduces the results.
- **PlatformIO in its own venv (`.pio-venv`, git-ignored).** PlatformIO pulls in many packages that the diagnosis code never needs; keeping it separate keeps `requirements.txt` minimal. Version 6.1.18.
- **Provenance on every record.** Each record in `sessions.jsonl` carries `source` (`sim` or `hardware`), `commit` (with `+dirty` when tracked files had uncommitted changes), `policy_hash` (first 12 hex digits of SHA-256 over the sorted policy JSON), `model`, `model_version` (Ollama digest, first 12 hex digits), `seed` and `timestamp` (ISO 8601, Africa/Lagos). Hardware records add `firmware` and `calibration`. Each run directory also has `meta.json`.
- **Records are appended as each trial finishes** (and flushed), so a run that is interrupted or crashes keeps everything up to that point.
- **`summary_table` refuses mixed sources.** It raises if sim and hardware records are passed together, so the two can never end up in one table by accident.
- **Legacy run `results/20261026-102515`** predates the provenance fields. It is a simulation run (no hardware existed). It is left unedited because `results/` is append-only; any loader treats a record with no `source` as `sim` and marks it legacy.
- **Model benchmark settings.** Thinking models (qwen3, qwen3.5) are benchmarked with reasoning switched off (`reasoning_effort: "none"` on Ollama, `enable_thinking: false` on llama.cpp). Measured on this Mac with the same first hybrid prompt: qwen3:8b took 26.7 s per call with thinking on (about 460 generated tokens) and 1.3 s with it off. At 10 to 20 calls per session and 340 LLM sessions in Phase 2, thinking on is not workable. `--think` keeps it available.
- **A model timeout counts as an invalid call and the hybrid falls back to the engine at once** (no retry: a retry would wait the full timeout again). A server that is down or refuses the request (`LLMUnavailable`) stops the whole run instead of producing a column of crashed trials.
- **Final held-out faults frozen on 26 Oct 2026** (working rule 6). H1 and H2 are now "development held-out". The final set, in `faultdiag/heldout.py`:
  - H3, element `main_wiring`: resistance between the battery terminal and the bus (corroded fuse holder or main wiring), 0.3 to 0.6 ohm against a healthy 0.01 ohm.
  - H4, element `current_sensor_src`: failing INA226 on the battery output channel, reading low with a gain of 0.45 to 0.65 (as after a calibration-register reset or a damaged shunt joint). It affects `read_current src` and the source current fields of both load tests.
  Both use elements already in the answer vocabulary, so no method gets a hint from new element names. They form the test set `heldout_final`, appended after TF2 so every earlier scenario keeps its seeds. `run_all` and `run_experiment.py` refuse them unless `--final` is given. Only bench-physics tests touch them before the final run; no method has been run on them, and no prompt or threshold has been tuned against them.
- **`FaultState.current_gain`** (new, default empty) carries a current-sensor gain error. Only the held-out module sets it; the engine's fault atoms never do, so the engine's model is unchanged.
- **Phase 3 transport: pyserial 3.5** (pinned in `requirements.txt`). It is the standard serial library for Python on macOS, Linux and Windows and has no dependencies of its own. It is imported only inside `SerialLink`, so simulation-only use does not need it.
- **Serial design.** One reader thread routes responses by id and handles events; one heartbeat thread sends a heartbeat each second when nothing else was sent, so a model that thinks for a minute does not trip the firmware's 3 s host-heartbeat cutoff. Timeouts come from `policy.json` (`timeouts_s.default` for readings; a load test adds its on-time; `timeouts_s.human_probe` for the technician). A late, duplicate or unknown response id is logged and dropped. A `hello` after connecting means the board reset: the session is marked interrupted and `BenchInterrupted` is raised on the next call.
- **The host waits out the firmware's thermal cool-down** (up to 30 s) instead of reporting a refused load test as a failed measurement. The firmware still enforces the limit; the host only avoids wasting the method's call.
- **Mock devices** (`faultdiag/mockdevice.py`) speak both firmware protocols with readings from the simulator, so the transport, the injector driver, calibration, the self-test script and the whole hardware runner are tested without a board, including over a real pseudo-terminal through pyserial. Anything run on them is labelled `sim` and saved under `results/mock-serial/`. The mock's cool-down can be shortened (`cooldown_scale`) for quick pipeline checks; the real firmware's cannot.
- **Hardware sessions are blind.** `run_hardware.py` writes session records without scenario or truth; the truth goes to `truth.jsonl` in the same run directory, which no method reads, and `grade()` joins the two only after the run ends. Blocks (scenario, trial) run in a random order; within a block every method runs on the same injected fault, in random order, so the comparison is paired.
- **Tool failures on hardware are injected in the host** (`ToolFailures`, between the policy guard and the bench), because the bench cannot be made to time out or return garbage on demand. Recorded in the truth file.
- **F1b is not run on hardware.** One series resistor (0.22 ohm) gives one severity, inside the simulator's "degraded" range.
- **Calibration** is a straight line per channel (reported = raw x gain + offset), fitted at three supply voltages (6, 10, 13 V) against the handheld meter. Records are dated files in `calibration/`, never overwritten. A hardware run refuses a board whose calibration id is not the latest record, or a record older than 30 days, unless `--allow-stale-calibration` is given. The firmware refuses gains outside 0.5 to 2 and offsets outside -2 to 2.
- **Noise refit rule** (`scripts/refit_noise.py`): simulator noise = median sample standard deviation of repeated raw readings, scaled by the gain; engine sigma = 3 x root-sum-square of that noise and the calibration fit residual (the same 3:1 margin as today's 0.03 V against 0.01 V). Before: `noise_v 0.01`, `noise_i 0.005`, `sigma_v 0.03`, `sigma_i 0.02`. After: **not yet run**, no calibration data exists. The script only proposes; applying it changes every simulated result, so it is a recorded decision, not an automatic step.
- **Test-load switch on the high side** (P-MOSFET with an NPN driver). The model returns the test load through the shared return (`ret`); a low-side switch with its source on `ret` would lose gate drive when H1 lifts `ret` by several volts.
- **Injector relay 1 moved from GPIO 14 to GPIO 27**: GPIO 14 toggles during ESP32 boot and would click a fault relay.
- **GUI stack: Python standard library only** (`http.server.ThreadingHTTPServer`, `sqlite3`) with hand-written HTML, CSS and JavaScript, charts drawn as inline SVG. No framework, no build step, no new dependency, and nothing to vendor: the page loads only files from `gui/static`, so it works with no internet. A framework (Flask, FastAPI, React) would add dependencies and a build for five pages that a 600-line script covers. One command starts it: `python -m gui`, on 127.0.0.1:8765 only.
- **Live updates by server-sent events, stored first.** Every step, engine update, model reply, warning and bench event is written to SQLite (WAL mode) and then pushed to each open tab. A tab that reconnects sends `Last-Event-ID` and the server replays what it missed, so several tabs, a sleeping laptop or a dropped connection all end up with the same picture. A new tab starts from the most recent session's first event.
- **One live session at a time**, in a background thread, so a stop, the safe-state button and the human-probe reply are handled while a model is thinking. A shadow `BayesEngine` follows the readings of whichever method runs, so the hypothesis chart and misfit flag are shown for every method, not only C and E.
- **Server restart mid-session:** a session cannot resume after its process died (the method's state is gone), so on start the server marks every session still `running` as `interrupted`, with a `session_end` event giving the reason. Interrupted and stopped sessions are not saved as results.
- **GUI sessions are saved** to `results/live/<source>-<date>/sessions.jsonl`, one directory per source and day, so sim and hardware stay apart. Mock-bench sessions are `sim`.
- **The safe-state latch is cleared only by a person.** The emergency button sends the firmware's `safe_state`; the GUI then refuses bench sessions until someone presses "Clear safe state" (the firmware's `resume`). It is never cleared automatically. The firmware's own limits apply whether or not the GUI is open.
- **Hardware scenario chosen by the server and hidden** in the live view until the session ends, then revealed with the grade. The frozen H3 and H4 are not offered in the GUI at all; they run only through `run_hardware.py --final` / `run_experiment.py --final`.
- **Experiments page numbers come from the CLI's text.** The summary table is the Markdown that `summary_table` (or `graded_summary` for blind runs) produces, parsed into a table in the browser, so the GUI cannot round differently from the CLI. A test compares it byte for byte with the run's `summary.md`.
- **The 14-day plan in the tracker is a proposal.** No plan existed in the repository; it was built from the steps in `docs/OWNER_TODO.md` and is editable. Bill-of-materials prices are left blank for the owner: none are invented.
- **Design:** system fonts with tabular figures, a cool grey-green page with white panels, one blue for data and one red reserved for danger and hardware (the safe-state button, hardware badges, failures). Dark mode follows the laptop setting. Tables scroll inside their panel on a phone; the page itself never scrolls sideways.
- **`results/live/` is git-ignored.** Sessions started from the GUI are demonstrations and checks, not the experiment; the reported results come from the CLI runs. They stay on the laptop and the Experiments page lists them as "GUI sessions".
- **Model shortlist** (48 GiB Apple M4 Pro; installed models from `ollama list`): llama3.2:3b (3B class, tool calling), qwen3:8b (8B class, tool calling), qwen3.5:9b (newer 9B, tool calling) and Bonsai-8B in 1-bit GGUF (`Bonsai-8B-Q1_0.gguf`) on llama.cpp. Left out: mixtral:8x7b (26 GB on disk, more than three times the 8B models, leaving little headroom beside the GUI and a browser; its speed was not measured), qwen3.5:27b (17 GB; three times the parameters of qwen3.5:9b, which already took a median 28 s per reply here, so 340 sessions of 10 to 20 calls each would take days), the community fine-tune `Qwythos-9B` (no published tool-calling evaluation, unclear provenance) and `llama3.2:latest` (the same digest as llama3.2:3b).

## Bayesian mathematical engine V2 (28 Oct 2026; experimental branch)

This work was done on `experiment/math-engine-v2`. The original method C remains unchanged; V2 is exposed as `bayes_v2_candidate` for paired simulation and later hardware evaluation.

- **Common-random-number particle bank.** The original finite Monte Carlo bank sampled healthy component tolerances independently under every hypothesis. That can create artificial Bayes evidence between nested hypotheses whose surviving sensors should be physically identical. V2 couples nuisance samples: particle `k` has the same healthy tolerances under every hypothesis, and a fault atom gets the same sampled severity everywhere it appears. A unit test asserts that an unobserved motor-tap sensor fault cannot acquire evidence from unrelated sensors.
- **Compute point: K=32 particles, N=64 future samples.** A sweep over K24/N64, K32/N64, K32/N96, K48/N64 and K48/N128 found K32/N64 gave 29/30 correct known cases and 9/10 tool-failure cases in the calibration subset, versus 28/30 and 9/10 at K48/N128, while reducing mean simulated wall time from about 1.23 s to 0.41 s. The larger bank was not consistently more accurate.
- **Decision-risk test selection.** V2 ranks actions by expected reduction in Bayes decision error per unit cost, while still reporting entropy EIG. This prevents tests that reduce uncertainty but are unlikely to change the diagnosis from dominating the policy.
- **Topology-aware current-balance falsification stays.** A cheap two-current conservation check is triggered only when the MAP explanation spans multiple independent downstream branches. On H2 (hidden load), the calibrated candidate uses this to reject the in-model motor+lamp explanation. An ablation showed RMS adequacy alone caught only 2/20 H2 trials and misdiagnosed 18/20; RMS plus balance caught 20/20. The balance layer therefore is not redundant.
- **History-wide model adequacy.** V2 reports the best single-hypothesis/single-particle RMS residual across the whole evidence history, in sigma units. Independent human DMM observations are included in the same joint residual. A provisional simulation threshold of **2.0 RMS-z after at least 3 scalar observations** was chosen because thresholds 1.25 to 2.0 all produced 0/110 false OODs on known development cases and 20/20 OOD on H1+H2; 2.0 is the most conservative value that retained the development result. Real calibration data must validate or replace this threshold before hardware claims are made.
- **Human DMM as a Bayesian sensor.** The DMM remains expensive (cost 10) and is selected by expected decision-risk reduction per cost. It is available after a failed automated tool and, optionally, when the posterior strongly implies a bad multiplexed sensor but still assigns meaningful mass to a sensor+physical-fault explanation. The frozen candidate uses sensor-fault mass >=0.50, nested sensor+physical mass >=0.15, and minimum decision-risk score 0.006. This improves C2/tool-failure recovery without making human measurement the default.
- **Frozen candidate parameters.** `BayesEngineV2HumanCoupled(n_samples=32, n_eig_samples=64, balance_z=6.0, cross_branch_only=True, allow_sensor_ambiguity=True, min_human_score=0.006, min_sensor_human_score=0.006, sensor_fault_mass_threshold=0.50, sensor_nested_pair_threshold=0.15, rms_misfit_z=2.0, rms_misfit_min_dof=3)`.

Broad paired development validation, 10 trials per scenario, same seeds as V1, excluding H3/H4:

| Set | V1 correct / OOD | V2 candidate correct / OOD | V1 mean cost | V2 mean cost |
|---|---:|---:|---:|---:|
| single (90) | 85 correct | 88 correct | 6.83 | 7.20 |
| compound (20) | 16 correct | 18 correct | 6.50 | 5.65 |
| development held-out H1/H2 (20) | 9 OOD | 20 OOD | 5.40 | 4.05 |
| tool failure (20) | 11 correct | 19 correct | 13.80 | 13.45 |

Across the 130 paired non-held-out trials, V2 was correct where V1 was wrong **14** times, V1 was correct where V2 was wrong **1** time, and accuracy tied **115** times. Mean measurement-cost delta was only **+0.069**, while mean simulated wall time was **0.593 s lower** per trial.

Residual limitations were inspected rather than tuned away:
- F4 seed 5008 never exposed an open lamp connection in any reading, so the history genuinely looked healthy.
- F5@load seed 8002 is the only paired loss where V1 was right: V2 over-called `battery + sensor_load` from a borderline source/load-sag pattern. No prior or fault-severity boundary was changed for this one seed.
- Two C2 misses stopped at `sensor_motor`; the physical+sensor alternative had only a few percent posterior mass, below the human-probe gate. Lowering the gate would buy more DMM probes and was not justified by the broad trade-off.
- TF1 had one `battery + motor_connection` over-call after a correct DMM connection-drop observation. This is retained as a residual ambiguity, not special-cased.

**Held-out provenance:** H3/H4 were already consumed in the Phase 2 final simulation on 27 Oct 2026, and their definitions existed in the repository before this V2 work. Therefore a new V2 run on H3/H4 cannot be presented as a pristine unseen simulation test. Any such run is post-hoc. The next meaningful validation is the real calibrated hardware bench, where V2 has not been tuned to measured noise or component tolerances.
